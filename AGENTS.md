# AGENTS.md

Repo is a NAS monitoring/management console for Immich + Nextcloud. Docs at repo root; Flask app is in `storage-control/`.

## Sources of truth

- `doc/system.md` — installed NAS hosts/paths. Its section «Журналы работы системы» is the map of every log location (journald vs. files, per service, with the commands to read them) — check it before hunting for logs anywhere else.
- `doc/pnan.md` — implementation plan.
- Executable config overrides docs. `storage-control/app/config.py` loads `.env` from the **repository root** via `Path(__file__).resolve().parents[2]`, despite `storage-control/README.md` saying `storage-control/.env`.
- If docs conflict with config or code, trust config/code.

## App shape

- Entrypoint: `storage-control/wsgi.py` -> `create_app()` in `storage-control/app/__init__.py`.
- Blueprints there: auth, dashboard, services, backups, planner (`/scheduler`), updates.
- All templates are under `storage-control/app/templates`; blueprints register it via `../../templates`.
- SQLite DB is auto-created at `$STORAGE_CONTROL_DATA/app.db`.
- Admin is seeded only if `ADMIN_PASSWORD` is set; an existing admin password is reset.
- APScheduler starts unless `ENABLE_SCHEDULER=false`; startup failure is logged but app still boots.

## Run / verify (from `storage-control/`)

- Install: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`
- Dev: `SECRET_KEY=... ADMIN_PASSWORD=... ENABLE_SCHEDULER=true .venv/bin/python -c "from wsgi import app; app.run(host='0.0.0.0', port=8765)"`
- Prod: `.venv/bin/gunicorn -w 1 -k gthread --threads 4 -b 0.0.0.0:8765 wsgi:app`
- User service is installed by `tools/install.sh`; it binds `0.0.0.0:8765` by default (all interfaces), so use firewall/nginx or install with `--bind 127.0.0.1:8765`.
- No automated tests. After edits: `.venv/bin/python -m compileall -q .`, then `curl -s http://127.0.0.1:8765/login`.
- Keep exactly one Gunicorn worker; long update/preserve jobs run in daemon threads and use subprocess.
- Update runs are serialized per target by `_start_update_run` (`updates/routes.py`, threading lock + a `running`-status check in the DB). A worker crash can leave an orphan `running` row that blocks that target's next update — reset its status in `update_run` manually before retrying. `systemctl start` on an already-active unit is a no-op return 0, so a runner's "start_service rc 0" does not prove the new binary was picked up; check `readlink /proc/$(systemctl --user show -p MainPID --value <svc>)/exe` when in doubt.

## Environment and data

- `SECRET_KEY`, `ADMIN_PASSWORD`, optional `ADMIN_USERNAME`, `STORAGE_HOME`, `STORAGE_CONTROL_DATA`, `ENABLE_SCHEDULER`.
- Data/logs/runs are under `$STORAGE_CONTROL_DATA` (default `/home/storage/.local/share/storage-control`).
- Disk discipline: `/mnt/backup/backups` holds backups only (pre-update dumps, preserves, rsync mirror); `/mnt/data` holds service data only (media, Immich, Stalwart RocksDB); all transient work (downloads, extraction staging) belongs in `/tmp`.
- `/tmp` is tmpfs (~7 GB). Enough for update tarballs/extracts (~150 MB), but don't stage GBs there.

## Dashboard and health gotchas

- App Health card must stay above Host; it shows service badges for Immich and Nextcloud plus current/available versions.
- App Health and service table depend on `/api/health/services`; the route stays in `dashboard/routes.py` because dashboard JS calls it.
- Other live endpoints are `/api/health/summary`, `/api/health/smart`, `/api/health/smart/status`, and `/updates/api/availability`.
- Dashboard version availability comes from GitHub Releases and is cached for about 5 minutes.
- Disks shows only physical block-backed filesystems; loop/virtual and non-`/dev/` devices are deliberately filtered in `app/collectors/system.py`.
- Temperature collection uses `psutil.sensors_temperatures()` with fallback to the `sensors` CLI.
- Fan support was removed as unused; do not reintroduce a `fans` field unless backed by real data.
- Jinja templates must have valid tag pairing; missing openers previously caused 500s.
- Python files must not end with stray markers such as `PY`.

## Update and preserve operations

- Updates page reports GitHub release availability and changelog for Immich and Nextcloud.
- `pnpm`/`node` for Immich live only in `~/immich/node/bin` (corepack shims) and are NOT on the storage-control service PATH; `runners/update_immich.py::_tool_env()` prepends that dir plus `COREPACK_ENABLE_DOWNLOAD_PROMPT=0` for the pnpm/build/migrations steps. Do not call `pnpm` bare in a runner.
- The pnpm version is pinned by upstream immich in `~/immich/src/package.json` (`packageManager: pnpm@11.27.1`) and corepack resolves that pin automatically. Never "upgrade" it locally: `corepack use pnpm@<x>` rewrites `packageManager` in an upstream file, which then makes the next `git checkout <tag>` fail and breaks `--frozen-lockfile` reproducibility. The "Update available! 11.27.1 -> 12.x" banner printed by pnpm is advisory only; the runner silences it via `NPM_CONFIG_UPDATE_NOTIFIER=false` and logs the effective version plus the pin in the `pnpm_version` step.
- `corepack use` must run in a real project directory (`~/immich/src`), never in `~/immich` — `~/immich` is not an npm project, and corepack silently bootstraps one there (stray `package.json` + `pnpm-lock.yaml` + `node_modules/`). Clean up such leftovers by deleting those three paths.
- Corepack on this host: `/usr/local/bin/corepack` (0.36.0, installed under `/usr/local/lib/node_modules/corepack-0.36`, also linked from `~/.local/bin` and `/usr/bin/corepack`) is the only working one. The Debian corepack 0.24 that used to ship in `/usr/bin` cannot run pnpm >= 11.27 (it hardcodes `bin/pnpm.cjs` and runs it in a `vm` context, so it dies with `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`); pnpm 12 also renamed its entry to `bin/pnpm.mjs`, which 0.24 never finds. Corepack 0.36 needs node `^22.22.2 || ^24.15.0 || >=26`; the system node is 22.22.1 and works anyway.
- Build JS step commonly fails because `npm` is absent on host; Nextcloud ships prebuilt `dist`, so this is usually non-fatal.
- Immich smoke test must poll, not fire once: `systemctl restart` returns before the API binds `:2283`. It hits `/api/server/ping` because `/api/health` is gone upstream and any unknown path returns 200 HTML from the SPA catch-all.
- `~/immich/.env` sets `IMMICH_PROCESS_INVALID_IMAGES=true` (added 2026-10-21). It is required because sharp decodes RAW (CR2/NEF/...) only with `failOn: 'none'`: libvips' tiff2vips cannot read a CR2 raw IFD (no `ImageLength`) and throws "TIFF directory is missing required \"ImageLength\" field" with the default `failOn: 'error'`. With it, Immich reads the embedded preview IFD and applies EXIF orientation itself. Without it every RAW asset fails thumbnail generation and — worse — the edit feature silently fails: `PUT /api/assets/:id/edits` returns 200 (it only stores metadata) while the UI waits for the `AssetEditReadyV2` websocket event that is emitted from `JobName.AssetEditThumbnailGeneration`'s `onDone`; the job dies, the 10 s `waitForWebsocketEvent` in `web/src/lib/managers/edit/edit-manager.svelte.ts` times out and the user sees "Не удалось применить изменения". A saved edit stays in `asset_edit` with `asset.isEdited = true` but no `*_preview_edited.jpeg` is produced, so the viewer keeps showing the original.
- The flag does **not** help 12-bit Samsung DNGs (Galaxy S25+): there libvips fails hard with "Input file has corrupt header: tiff2vips: samples_per_pixel not a whole number of bytes" — 3 samples x 12 bit = 4.5 bytes, not a whole number — and no `failOn` setting changes that. The fix is the system config **`image.extractEmbedded = true`** (set 2026-10-22): `MediaService.extractOriginalImage` then pulls the embedded `PreviewImage` out of the DNG with exiftool instead of decoding the raw IFD, and applies `asset.exifInfo.orientation` to it (the embedded JPEG has no orientation of its own, so the DNG's EXIF orientation is authoritative). The edit pipeline works again — `AssetEditThumbnailGeneration` produces `*_preview_edited.jpeg` — and the previews come out with the right orientation. 16-bit DNGs without a `PreviewImage` tag still fail, but with a different error ("vips_colourspace: no known route from 'multiband' to 'rgb16'"); they keep their old previews.
- Regenerating previews after this change: `POST /api/assets/jobs` with `{"name":"regenerate-thumbnail","assetIds":[...]}` (the enum values are kebab-case, *not* the `JobName` constants from `server/src/enum.ts`). Only regenerate the affected files — the flag changes the source for every RAW, and a blanket "regenerate all" would rewrite ~10k previews. Check the result with `exiftool -s -ImageWidth -ImageHeight <preview>`, not `identify`: ImageMagick applies the EXIF orientation when reporting, so it shows the *displayed* size and makes a correct preview look wrong.
- The core workflow plugin is loaded from `~/immich/build/plugins/immich-plugin-core/{manifest.json,dist}` (that is the `server/Dockerfile` layout; the old `build/plugins-core-dist` symlink was never read by anything). Missing it logs `Failed to import plugin ...` on every boot. Rebuild: `pnpm --filter @immich/sdk --filter @immich/plugin-sdk --filter @immich/plugin-core build`, then copy `packages/plugin-core/{manifest.json,dist}` there. It needs `extism-js` (`~/immich/tools/extism-js`) and `wasm-merge` (`~/immich/tools/binaryen/binaryen-version_124/bin`) on PATH — neither is on the service PATH.
- Nextcloud updates must fetch without recursive submodules: use `git fetch origin --tags --no-recurse-submodules`; the runner already does.
- After checkout, Nextcloud needs `git submodule update --init --recursive`. If this is skipped, `3rdparty` stays on the old commit and `occ upgrade` can fail with missing paths / Symfony errors.
- `occ upgrade` may exit 1 due to stale optional app references even when status and DB are fine. Verify `php occ status`, especially `versionstring`, `maintenance`, and `needsDbUpgrade`.
- `runners/update_nextcloud.py` has a `viewer_sync` step (after `restart_services`): `/apps*/*` is git-ignored, so checkout never refreshes the bundled-but-separate `viewer` app, and on a major jump Nextcloud disables it — office files then download instead of opening Collabora, because the `LoadViewer` event never fires and richdocuments never registers its handler. The step re-extracts `apps/viewer` from `https://download.nextcloud.com/server/releases/nextcloud-<tag>.tar.bz2` (viewer is not on the app store, so the release tarball is the only source) and re-enables it. Patch updates just compare `<nextcloud max-version>` in `appinfo/info.xml` and skip the ~250 MB download.
- Preserve snapshots live under `/mnt/backup/backups/preserves` and are tracked in `update_preserve`. They support prepare, restore, delete, and live logs through `/updates/preserve/<id>/{log,api,...}`.
- `~/immich/src` no longer carries local patches — the `checkDiskUsage` (`frsize` -> `bsize`) patch was removed on 2026-10-21 after the Node runtime was upgraded (see below). The runner's `apply_local_patches` step tolerates an empty/missing `tools/immich/patches/` dir (logs "no local patches", rc 0). The patch commit lives on in `~/immich/src` as tag `local/statfs-bsize-patch` (0dab4eb7e); this repo's history keeps only the format-patch file (`git show 3f5596e:tools/immich/patches/0001-storage-statfs-bsize.patch`, re-appliable with `git am`) — the commit object itself was never in this repo. The branch `local/patches` was deleted. Identity in the immich repo is repo-local `storage <storage@nas.local>`; never push anything there upstream (origin is immich-app/immich). If the patch is restored (Node rolled back below 24.16.0), reset `server/src/repositories/storage.repository.ts` with `git checkout --` before the next immich update: `_patched_files()` finds nothing in the now-empty `tools/immich/patches/`, so the runner's pre-checkout reset cannot clean the tree and `git checkout <tag>` would abort with "Your local changes ... would be overwritten".
- Node runtime: `~/immich/node/bin/node` was upgraded **v24.15.0 -> v24.22.1** on 2026-10-21 (the old install is kept as `~/immich/node.bak-24.15.0` for rollback). Why it matters: `fs.statfs().frsize` exists only on Node >= 24.16.0 (`nodejs/node#62277`), and upstream Immich commit `3af49d9b4` (#31983, in v3.3.0) switched `checkDiskUsage` to `stats.frsize` — on 24.15.0 that yields `NaN` for `diskSize`/`diskAvailable`/`diskUsagePercentage`. v24.22.1 is the version upstream pins in `.nvmrc` for v3.3.5. ABI is unchanged (modules 137), so sharp/bcrypt/msgpackr native addons were not rebuilt. The official tarball ships no `pnpm`/`yarn` corepack shims (nor did v24.15.0 — the ones in that install were created by hand), so they must be re-created as symlinks to `../lib/node_modules/corepack/dist/{pnpm,pnpx,yarn,yarnpkg}.js` after every reinstall, or the update runner's `pnpm` will resolve to a shim outside `~/immich/node/bin`.
- Prepare stashes local Git changes before backup, so preserve's file copies may predate the stash. For custom tracked files such as `.htaccess`, recover them from `git show refs/preserve/<id>:...` rather than from the copied file.
- On failure the runner turns maintenance mode off where possible; verify it manually before retrying.

## Stalwart

- Runs as a **user** systemd unit (`systemctl --user stop/start/status stalwart.service`, unit at `/home/storage/.config/systemd/user/stalwart.service`) — system-wide `systemctl` won't see it, and its controls need no sudo.
- Install: `/home/storage/stalwart/{bin/stalwart,etc/config.json}`; RocksDB data at `/mnt/data/stalwart` (the unit pins `RequiresMountsFor=/mnt/data/stalwart` and `StartLimitIntervalSec=0` so it survives a not-yet-mounted data disk).
- `etc/config.json` contains only the store pointer (`{"@type":"RocksDb","path":"/mnt/data/stalwart/"}`). Admin UI answers at `http://127.0.0.1:8082/admin/` — that is the runner smoke target (`runners/update_stalwart.py::_smoke`). With `config.json` missing, Stalwart boots in bootstrap mode with WebUI on `:8080`. Version check: `~/stalwart/bin/stalwart --version`.
- Update runner staging: downloads/extracts only into `/tmp/stalwart-update-<run_id>_*` (auto-cleaned on success **and** failure); the pre-update binary goes to `/mnt/backup/backups/stalwart/<run_id>/stalwart.bak` — a real backup artifact, like the immich/nextcloud pre-update dumps.
- Cross-filesystem gotcha: `/tmp` is tmpfs, so `os.replace(tmpfile, /home/...)` fails with `[Errno 18] Cross-device link`. The runner works around it by `copy2`-ing to `stalwart.new` next to the target and `os.replace`-ing within `/home`'s filesystem. Never stage runner work on `/mnt/data` or `/mnt/backup` (disk discipline above).
- SMTP/delivery logs are NOT in journald — only `/var/log/stalwart/stalwart.<date>` has them. Submission goes through listener `submissions` on port **8465** (not 587). Delivery verification: `grep -E "delivered|gmail" /var/log/stalwart/stalwart.<date>`; look for `delivery.delivered` (the receiving server's name is in `hostname`, e.g. `gmail-smtp-in.l.google.com`) and for `smtp.dkim-pass` / `smtp.dmarc-pass` / `smtp.iprev-pass` / `smtp.spf-from-pass` (each has a `*-fail` counterpart). `code = 250, details = "OK"` appears in **local** delivery (DSN inside the server, `hostname = "localhost"`), not in Gmail acceptance. Log lines carry ANSI colour codes — strip them with `sed 's/\x1b\[[0-9;]*m//g'` before reading fields. Full map: `doc/system.md` → «Журналы работы системы».
- Message-ID / Date headers for outgoing mail are added via settings `session.data.add-headers.message-id` / `session.data.add-headers.date` = `true` (set in WebUI). Without them Gmail rejects with `5.7.1`.
- DKIM signing works via a `DkimSignature` management-JMAP object. **The WebUI key generator is broken in 0.16.27** (ed25519: `InvalidEncoding`; RSA: `no items found ... Failed to build RSA key`). Working procedure, bypassing the UI (done 2026-10-20, selector `nas`, id `jkmvl2saaaaa`):
  - Admin CLI: `/home/storage/.local/bin/stalwart-cli` (v1.0.13, from `stalwartlabs/cli` releases). Auth by env: `STALWART_URL=https://mail.itexperts.team STALWART_USER=<admin login> STALWART_PASSWORD=...`; `-k` skips self-signed TLS verification. Schema is fetched from the server and cached in `~/.cache/stalwart-cli/` — useful to inspect exact field shapes there when `describe` can't express them.
  - Key file: generate locally (`openssl genrsa -out ~/stalwart/etc/nas_rsa.key 2048`), pass as **File variant of SecretText**: `--field 'privateKey={"@type":"File","filePath":"/home/storage/stalwart/etc/nas_rsa.key"}'`. Server's crypto layer (ring) rejects RSA < 2048 bits with `TooSmall`; ed25519 build also fails — use RSA-2048.
  - Create: `stalwart-cli -k create DkimSignature/Dkim1RsaSha256 --field domainId=b --field selector=nas --field 'privateKey={<SecretText File variant>}' --field 'headers={"From":true,"To":true,"Date":true,"Subject":true,"Message-ID":true}' --field canonicalization=relaxed/relaxed --field stage=active --field report=true`. Gotchas: `headers` must be a **map of booleans** (JSON array is rejected: `headers requires a JSON object/array value` then `Invalid value for object property`); `id` is NOT a create field (server autogenerates, e.g. `jkmvl2saaaaa`); `domainId` is the Domain object's JMAP id (`b` for itexperts.team, listed by `stalwart-cli -k query Domain`).
  - DNS: reg.ru auto-splits long TXT values into multiple strings (our 410-char `v=DKIM1; k=rsa; p=...` went out as two chunks and validates fine). Verify via `dig +short TXT nas._domainkey.itexperts.team @ns1.reg.ru` and check the SOA serial moved — reg.ru publishing was stuck for a day (serial frozen at one value) but recovered on its own.
- Outbound mail authentication is fully green (verified via Gmail "Show original" 2026-10-20): `dkim=pass (s=nas)`, `spf=pass client-ip=149.62.52.187`, `dmarc=pass`. The published DNS (reg.ru): SPF TXT on `@` = `v=spf1 ip4:149.62.52.187 -all`; `_dmarc` TXT = `v=DMARC1; p=none; rua=mailto:stas@itexperts.team` (raise to `p=quarantine` later, after reports accumulate); MX = `home.itexperts.team`. DKIM signature object id `jkmvl2saaaaa` (selector `nas`).
- Outbound SMTP egress path: NAS (`10.216.50.50`, LAN `10.216.0.0/16` on `br-lan`) → OpenWrt router ("RouteRich", `wan/eth1`, static `149.62.52.187`, PTR `mail.itexperts.team`) → internet. The router runs the `pbr` (Policy-Based Routing) package; a policy named "SMTP direct" (`ip saddr 10.216.50.50 tcp dport 25` → fwmark → `pbr_wan` table → WAN) forces outbound SMTP off the alternative egress (`84.32.99.227`, a cherry-servers path) because SPF is published only for `149.62.52.187` — if that policy is lost/removed, Gmail sees `spf=fail` again and the hard `-all` in our SPF record will get mail rejected.
- Debugging egress truth: the only trustworthy test for "which IP does my SMTP mail leave from" is the receiving side — Gmail "Show original" `Received:`/`client-ip=...`, or router-side `nft list ruleset | grep snat` / conntrack. Do NOT trust `curl ifconfig.me` from an agent/sandbox shell (it reported a cherry egress that had nothing to do with the mail path).

## Host backups

- `backup-immich-nc.timer` (04:00) runs `tools/backup_immich_nc.sh`: immich/nextcloud DB dumps plus stalwart RocksDB data/config, immich `.env`, nextcloud `config.php`, nginx/letsencrypt and `postgresql.conf`/`pg_hba.conf` (via sudo) to `/mnt/backup/backups`, 14-day rotation. The script lives in this repo; the stale copy that wrote to the non-existent `/mnt/recovery` is gone.
- `backup-home-rsync.timer` (05:00) runs `tools/backup_home_rsync.sh`: an rsync mirror of `/home/storage` to `/mnt/backup/backups/home-storage/{current,deleted,logs}`, excluding `/.cache/`. `/` and `/home/storage` both sit on the system disk `/dev/sdd2` (298 GB); the previously failing `/dev/sde` is no longer present in `lsblk`, but the mirror is still the main protection for the home directory. Media lives on `/mnt/data` (RAID1 `md0` from `sda`+`sdb`) and is not copied.

- `Runner app/runners/smart_monitor.py` performs the nightly SMART check; it stores `SmartDiskState` and active `SmartAlert` records. Startup also runs one baseline check asynchronously.
- SMART discovery is dynamic from `/sys/block`; loops, RAID, RAM, empty, and virtual block devices are excluded.
- Dashboard renders SMART alarm rows red and lists active alarms from `/api/health/smart/status`.
- `tools/immich/night_fix_thumbnails.cjs` is the user's own nightly thumbnail fixer, run by `immich-nightfix.timer` (03:30). It lives in this repo, not in `~/immich/src`, because Preserve's `git stash push -u` would swallow it as an untracked file. It loads `sharp`/`pg`/`thumbhash`/exiftool from immich's `node_modules` via `createRequire`. It is started through `tools/immich/night_fix_wrapper.sh`, which absorbs the sharp/libvips native teardown crash: 24.15.0 died with SIGABRT (134), 24.22.1 with SIGSEGV (139). The crash destroys the script's own exit code (with sharp loaded, `process.exit(0)` and `process.exit(1)` both end up as 134/139), so the wrapper recovers the outcome from the script's output instead: `nothing to fix` and `done: N fixed, 0 failed, 0 still without preview` → exit 0, any other `done:` line → exit 1, no marker at all → the signal code is propagated (crashed mid-run). Output is streamed to the journal with `tee`, so a killed run still leaves its progress behind. There is no separate log file: the unit sets no `StandardOutput=`, so everything lands in the persistent user journald — `journalctl --user -u immich-nightfix.service`. Since 2026-10-21 it is a **fallback only**: it selects just the assets that have no preview at all (no `asset_file` row with `type=preview`/`isEdited=false`, or the file is missing on disk) and never overwrites existing previews — those are Immich's own now. Rows are written with `ON CONFLICT ("assetId", type, "isEdited") DO UPDATE` because that triple is a unique index. RAW previews get the EXIF orientation applied in the script (`ORIENTATION_TO_SHARP_ROTATION`, mirrored from `server/src/constants.ts`) because the embedded preview carries no Orientation tag and would otherwise sit sideways; `exiftool -auto-orient` does **not** work here — it is a write-time option and is ignored by `-b` extraction.

## Nextcloud Whiteboard

- Whiteboard is a Nextcloud app (`/home/storage/nextcloud/apps/whiteboard`, app-store v2.0.0) plus a separate Node Socket.IO server extracted (not a git clone) at `/var/lib/whiteboard-websocket/`, run by system unit `whiteboard-websocket.service` on port **3002** (`/etc/systemd/system/whiteboard-websocket.service`). Node is `/home/storage/immich/node/bin/node`, which is not on the default PATH.
- Unit env: `NEXTCLOUD_URL`, `PORT=3002`, `JWT_SECRET_KEY`, `STORAGE_STRATEGY=lru`, `MAX_UPLOAD_FILE_SIZE=20`, `TLS=false`, `CHROME_EXECUTABLE_PATH`. The `JWT_SECRET_KEY` env must equal `occ config:app:get whiteboard jwt_secret_key` (shared secret; the value lives in the DB and the unit — never commit it). `collabBackendUrl` must be `https://drive.itexperts.team/whiteboard`.
- Two nginx layers: `sites-enabled/proxy-sites` (:8080, public TLS) proxies `drive.itexperts.team` to the inner `sites-enabled/nextcloud` (:8443), which proxies `/whiteboard/` to `127.0.0.1:3002`. **Both** the outer `drive.itexperts.team` block **and** the inner `/whiteboard/` location must set `proxy_http_version 1.1` + `proxy_set_header Upgrade $http_upgrade` + `proxy_set_header Connection $connection_upgrade`; if the outer block omits them it strips the upgrade, the inner `$http_upgrade` is empty, no `101` is returned, and the client shows a websocket error. `map $http_upgrade $connection_upgrade` lives in `/etc/nginx/conf.d/websocket.conf`.
- Two local patches are lost on app/server update. `apps/whiteboard/lib/Listener/AddContentSecurityPolicyListener.php` adds `https://esm.sh` to `font-src` (excalidraw fonts; without it the browser logs a CSP `font-src` error). `websocket_server/Services/SocketService.js` sets `path: '/whiteboard/socket.io/'` (the server is mounted under `/whiteboard/`; upstream sets no `path` and `Config.js` has no path option). The app-store signature can't be regenerated, so `occ integrity:check-app whiteboard` reports one `INVALID_HASH` for the listener (cosmetic; `integrity.check.disabled => true` silences it).
- Verify: `curl -sk --http1.1 --max-time 5 -H 'Upgrade: websocket' -H 'Connection: Upgrade' -H 'Sec-WebSocket-Version: 13' -H 'Sec-WebSocket-Key: AAAAAAAAAAAAAAAAAAAAAA==' -o /dev/null -w '%{http_code}\n' 'https://drive.itexperts.team/whiteboard/socket.io/?EIO=4&transport=websocket'` → `101`. `--http1.1` is required: the outer nginx negotiates HTTP/2 by default, and a websocket upgrade cannot ride on h2 (the `Upgrade:` header is dropped, and socket.io answers `400 {"code":3,"message":"Bad request"}` instead of `101`). The admin "verify connection" test succeeds when the server answers `connect_error` with the message `Connection verified`.
- Recording (`RecordingControlService.checkAvailability`, run on every socket connect) launches headless Chromium through `puppeteer-core`, which needs an explicit binary. The host has no packaged `chrome`/`chromium`, and `ConfigUtility.js` auto-detect fails because `playwright-core` 1.63 resolves `chromium-1243` while only `chromium-1248` is installed. The unit therefore pins `CHROME_EXECUTABLE_PATH=/home/storage/.cache/ms-playwright/chromium-1248/chrome-linux64/chrome` (an existing Playwright Chromium). If Playwright changes the revision, update the path or install a system Chrome. Failure shows as a UI toast `Chromium failed to start (…)` and `[Puppeteer] Launch check failed` in the journal.
- Don't trust an unauthenticated CSP probe: `curl -sk -I https://drive.itexperts.team/apps/files/` returns `401` with `font-src 'self' data:` and looks like the font bug, but the real authenticated page serves `font-src 'self' data: https://esm.sh`. Verify with a throwaway app password: `occ user:add-app-password <user>`, then `curl -sk -u '<user>:<pw>' -D- -o /dev/null https://drive.itexperts.team/apps/files/ | grep -i content-security-policy`, and delete the token afterwards (`occ user:auth-tokens:list` / `delete`). Running `occ` here needs `chmod 660 config/config.php` first (restore to `640` after).
